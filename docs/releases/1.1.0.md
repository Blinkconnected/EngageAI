# Release Report — v1.1.0

**Date**: 2026-08-05
**Channel**: **stable** — the first non-pre-release build
**Scope**: The beta programme's accumulated work, released together, plus
one previously-undiscovered defect found while writing the platform
engineering handbook and fixed before shipping.

---

## Summary

This is the release where the version string stops carrying a `-beta`
suffix. Nothing about the delivery mechanism changed for it: the same
three files that have always had to agree still agree, the changelog is
still the source of truth for what the running build calls itself, and
the channel (`stable`) is still *derived* from the version string rather
than authored beside it.

Two things belong in a release report rather than only in the changelog.

**A defect that had never run in production, found by writing
documentation.** While tracing the platform's events end to end for
[the handbook](../architecture/platform-handbook.md), one routing key —
`conversation.reopened` — turned out to be bound by a consumer and
published by nothing at all. Its handler existed, was tested, and had
never once executed against a real event.

**A structural guard so that class of defect cannot recur.** The fix for
one orphaned binding is a publisher. The fix for *orphaned bindings* is a
test that fails when one exists, and that is what shipped alongside it.

---

## The defect

`learning-signals-consumer` has bound `conversation.reopened` since the
day it was written. Its own module docstring calls that key
*"the one that matters most: it invalidates a resolution outright."*

Nothing published it.

- `ConversationService.update()` emitted `f"conversation.{status.value}"`
  and only for the two **terminal** statuses (`resolved`, `closed`). A
  transition *out of* a finished status published nothing under that
  name.
- `conversation_ingest_consumer` — the far more common path, a customer
  writing back — flipped the status to `WAITING`, cleared `closed_at`,
  and published nothing at all.

### Why it survived

Every test covering the consumer fabricated the event dictionary and
called `handle_event` directly. The binding therefore looked thoroughly
tested while the routing key had no producer anywhere in the platform.

This is the same blind spot recorded in
[`event-bus.md`](../architecture/event-bus.md)'s incident section, where
the outbox relay published nothing for months while every consumer test
passed. Stated once, plainly, because it is the lesson rather than the
instance:

> **A test that exercises a handler is not a test that exercises the
> pipeline.**

### What it cost

An observation that had already settled kept an outcome claiming the
conversation was `resolved`, and `first_contact_resolution=True`, after
the customer had contradicted both by writing back. Every counter looked
healthy, because the record simply never received the news.

Nothing downstream consumed those observations yet — Learning phase 1
observes and proposes nothing — so no customer-visible behaviour was
wrong. What was wrong was the measurement that phase 2's go/no-go
decision depends on.

### A second bug behind the first

Even with the event published, `learning-signals-consumer` never set
`reopened_at` on its `OutcomeInputs`, so `conversation_outcome.derive`
would have answered `reopened=False` for the one event whose entire
purpose is to say a resolution did not hold. Both halves are fixed
together; fixing only the publisher would have produced an event that
still changed nothing.

## Technical changes

- **`ConversationService.update()`** publishes `conversation.reopened`
  when a status transition leaves `FINISHED`. The payload carries
  `previous_status`, `status`, `ended_at` and `reopened_at`.
- **`conversation_ingest_consumer`** publishes the same event on the
  customer-message reopen path, reading `closed_at` **before** clearing
  it.

  `ended_at` is carried **by value** rather than left for a consumer to
  read back, because this handler clears the only column it lives in — by
  the time any consumer sees the event, when the conversation had ended
  is a fact only the publisher still holds.
- **`learning_signals_consumer`** reads `reopened_at` and `ended_at` off
  the payload for that event type and passes both into `OutcomeInputs`. A
  malformed timestamp answers `None` rather than raising: a signal is an
  optimisation over the settle sweep, and a bad timestamp must not park a
  message in a redelivery loop when the sweep would have settled the
  observation anyway.
- **`LearningObservationService.attach_outcome()`** returns an
  observation whose outcome is no longer settled to `pending`, and clears
  `settle_due_at` when the conversation is not resolved.

  Without this, a reopen produced a row that was simultaneously `ready`
  and unsettled — a state the settle sweep (which claims on
  `state == pending`) could never correct — and a settle deadline
  computed from the resolution the conversation had just lost, which
  would have had the sweep promote it straight back.
- **`_TERMINAL_EVENT`** replaces `f"conversation.{status.value}"` with an
  explicit `{status: event_name}` mapping. Every event type this codebase
  publishes is now a literal somewhere in the source. A name assembled at
  runtime is invisible to a reader, to a grep, and to a static guard —
  which is precisely how the orphaned binding went unnoticed.

## The guard

`tests/unit/test_bound_routing_keys_have_publishers.py` — static, like
`test_ownership_is_the_only_writer.py`,
`test_memory_manager_is_the_only_writer.py` and
`test_learning_writes_only_its_own_tables.py`, and for the same reason:
a behavioural test covers the paths somebody thought to write, and this
covers the bindings nobody has written yet.

Every non-wildcard routing key declared in any consumer's `ROUTING_KEYS`
must appear as a string literal in some **other** module under `src/`.
Wildcards (`#`, `*`) are out of scope — they match by pattern, so they
are deliberately unresolvable to a specific publisher.

Three properties, each deliberate:

- **Bindings are read by importing the consumer, not by parsing it.**
  `notification_consumer` computes its keys from
  `NotificationRuleRegistry` at import time, so a source-level read would
  see a function call instead of the keys a running consumer actually
  binds.
- **Docstrings are excluded from the publisher search.** A routing key
  *named in prose* is exactly what `conversation.reopened` had; counting
  it would have made the guard pass on the bug it exists to catch.
- **The guard's own coverage is asserted.** One test proves the search
  returns nothing for a key published nowhere, and another fails if
  `_bindings()` ever silently returns an empty set — which would let the
  primary test pass by having nothing to check, and read exactly like
  coverage.

**Verified by watching it fail.** With the two new publishers temporarily
renamed, the guard reports:

```
'conversation.reopened' (bound by
  blinkengage.infrastructure.events.consumers.learning_signals_consumer)
```

and passes once they are restored. A guard nobody has watched fail is a
guard nobody knows works.

## A capability this unlocks, for free

`workflow_definitions.trigger_event_type` is a free string, and the
workflow engine binds `#` — so a company can now build an automation on
**"conversation reopened"** (escalate it, tag it, notify a supervisor,
route it to a senior queue) with no further work. That was impossible
before, not because the engine refused it, but because a rule configured
against that trigger would have sat there and never fired.

Two related checks were made rather than assumed:

- **The payload needs no audit redaction.** It carries ids, statuses and
  timestamps only — no `body`, `note` or customer name — so it does not
  join `_REDACTED_PAYLOAD_FIELDS`. A reopen event landing verbatim in
  `audit_logs` (longer retention, different permission) copies no
  customer content.
- **No frontend trigger picker had to change**, because Workflows has no
  UI yet (handbook §37, limitation #30). Nothing hardcodes a list of
  trigger event types that would have silently omitted the new one.

## Known issues / limitations

Carried forward from the handbook's §37, unchanged by this release:

- **`AnswerVerifier` does not exist** (B8), so *"official knowledge
  wins"* is enforced on the Memory side and advisory on the answer side.
- **Knowledge versioning is designed, not built** (B9) — a citation is
  not reproducible.
- **`retrieval_traces` does not exist** (B10) — gap detection will lose
  its retrieval half.
- **Learning cannot separate a workflow close from a human close** on the
  data available in phase 1; an unassigned close answers `unknown`, which
  is not attributable.
- **No TLS, seven placeholder secrets in the live `.env`, no off-host
  backups, no MinIO backup, a placeholder alert destination, and a
  placeholder CI deploy target.** These are deployment decisions rather
  than code defects and are tracked in
  `docs/deployment/go-live-checklist.md`. **A stable version number does
  not close them**, and this report says so rather than letting the
  absence of a `-beta` suffix imply otherwise.

## Concurrent work, and what is *not* in this release

**Learning phase 2 — clustering, trend detection and anomaly detection —
landed in the working tree while this release was being prepared.** Four
tables, one migration (`f6c3d95a2e81_learning_clusters`), five
`/intelligence/*` endpoints, its own sweeps, and roughly a hundred tests.

It is **not in 1.1.0.** Its changelog entry sits under `## [Unreleased]`,
which is correct and was left alone: this release ships what was verified
for it, and nothing else. `1.1.0` is defined by its changelog entry, not
by whatever the working tree happens to contain.

Two consequences worth stating plainly rather than discovering later:

- **A real tag must be cut from a commit that excludes phase 2**, or
  phase 2 should be folded into a later release with its own report. The
  version files say `1.1.0` while the tree also holds post-1.1.0 work;
  that is normal for a working tree and wrong for a tag.
- **The handbook's counts are the released platform's**, not the tree's.
  The tree currently reports 97 tables, 84 migrations, 320 routes and
  3,346 tests. The handbook says so explicitly rather than tracking a
  moving branch.
