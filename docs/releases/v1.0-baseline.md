# Version 1.0 Baseline

**The architectural reference for all future development.**

This document states what Blink Engage *is* at the first production
release: its shape, its invariants, what owns what, and which decisions
are settled. Future work is measured against this. When a change
contradicts something here, the contradiction is the thing to discuss —
either the change is wrong, or this document needs revising with an
argument attached.

- **Baseline commit:** `08a9147`
- **Baseline date:** 2026-08-06
- **Audit:** [RC1 Engineering Audit](./v1.0-engineering-audit.md)

> **On the version number.** The repository already ships `1.1.0`
> (`pyproject.toml`, `package.json`, `CHANGELOG.md`) — releases 1.0.0 and
> 1.1.0 were cut during development. "v1.0" in these documents means
> *the first production release*, not a version string to roll back to.
> **Tag GA as `v1.2.0`** so the published history stays monotonic; going
> backwards to `1.0.0` would make every previous artefact look newer than
> production. This is a decision for the release owner, flagged here
> rather than made silently.

## 1. What the platform is

An enterprise omnichannel customer engagement platform. Customers reach a
company through WhatsApp, Facebook Messenger, Instagram, Telegram, email,
SMS or web chat; those messages become **conversations**; conversations
are routed to **queues**, assigned to **agents**, measured against
**SLAs**, and optionally answered by **AI**.

Multi-tenant: one deployment serves many companies, isolated at the
database row level and enforced in the application layer.

## 2. Architecture

### 2.1 Layers

Clean Architecture, enforced by import direction. Dependencies point
inward only.

| Layer | Files | Lines | May import |
|---|---|---|---|
| `domain/` | 87 | 20,282 | nothing outside itself |
| `application/` | 101 | 27,294 | `domain` |
| `infrastructure/` | 243 | 40,341 | `domain`, `application` |
| `api/` | 106 | 19,646 | `domain`, `application`, `infrastructure` |
| `core/` | 18 | 2,418 | cross-cutting: config, logging, DI, correlation |

**`domain/` performs no I/O.** No database session, no HTTP client, no
broker. It holds entities, value objects, invariants and pure decision
functions. This is the single most load-bearing rule in the codebase: it
is why business rules are testable without a database, and why the same
rule cannot quietly acquire two implementations.

### 2.2 Patterns

| Pattern | Where | Why |
|---|---|---|
| Repository | `infrastructure/repositories/` | Application code depends on a collection interface, not on SQLAlchemy. |
| Dependency injection | `core/container.py` | Wiring is explicit and overridable in tests. |
| Transactional outbox | `event_outbox` → relay | An event cannot be published unless the business change committed. |
| Service layer | `application/services/` (93) | One place per use case; endpoints stay thin. |
| Structural guard tests | `tests/unit/test_*_guard*.py` | Invariants that a reviewer would otherwise have to remember. |

### 2.3 The guard tests

Several invariants are enforced by tests that fail the build rather than
by convention. They exist because each one has already been violated
once:

- **One resolver per configuration fact.** Configuration resolves through
  Service → Queue → Company → Platform, and there is exactly one chain.
  Nine competing fallbacks once disagreed.
- **Every production service is bounded.** Memory limit, restart policy,
  health check, log rotation. Three services once ran with none.
- **The replay tool knows every queue.** Adding a consumer without
  registering it fails the build, or its dead-letter queue is one nobody
  can drain.
- **Bound routing keys have publishers.** A consumer bound to an event
  nothing emits is dead code that looks like coverage.
- **Version consistency.** `CHANGELOG.md`, `pyproject.toml` and
  `package.json` must agree.

**Adding a guard is the preferred response to "we must remember to…".**

## 3. Data flow — a message becomes a reply

```
  channel webhook
        │
        ▼
  POST /api/v1/channels/webhook/{provider}
        │  (signature verified, tenant resolved)
        ▼
  message.received ──────────► event_outbox (same transaction)
        │
        │ relay-event-outbox, every 5s
        ▼
  blinkengage.events (topic exchange)
        │
        ├─► conversation-ingest ─► Conversation + Message rows
        │        │
        │        └─► message.persisted
        │                 ├─► ai-autopilot      (may the AI answer? answer.)
        │                 ├─► notifications     (tell an agent)
        │                 └─► usage-metering    (record billable usage)
        │
        ├─► audit-log        (everything, always)
        └─► workflow-engine  (everything, customer-defined triggers)
```

Every hop carries a **correlation id**: the inbound request's header, or
a fresh one, threaded through the outbox row, the AMQP message property,
the consumer's log lines, and any Celery task the work spawns.

## 4. Invariants

These are settled. Changing one is an architectural decision, not a
refactor.

1. **Tenant isolation is enforced in the application layer**, on every
   query, via the company scope. There is no cross-tenant read path.
2. **`domain/` does no I/O.**
3. **Domain events are written through the outbox**, in the same
   transaction as the change that caused them. Never published directly.
4. **Consumers are idempotent.** Delivery is at-least-once; a redelivered
   message must not double-charge, double-notify or double-write.
5. **A failing message is retried, then quarantined** — never requeued in
   a hot loop, never dropped.
6. **The audit trail is append-only** and is not subject to retention.
7. **Configuration resolves through exactly one chain.**
8. **An undispatched outbox row is never deleted**, at any age.
9. **Secrets never enter version control.** Encrypted at rest via
   `CREDENTIALS_ENCRYPTION_KEY`; supplied by environment.
10. **Migrations are reversible** unless they are data repairs, and then
    the file says why.

## 6. Queue register

12 consumer queues. Uniform policy, no exceptions:

| Property | Value |
|---|---|
| Attempts | 5, including first delivery |
| Backoff | 1s → 4s → 16s → 64s → 256s (base 4, capped 300s) |
| Retry mechanism | `<queue>.retry`, per-message TTL, dead-lettered back |
| Quarantine | `<queue>.dlq` with error, traceback, attempt count, correlation id |
| Replay | `scripts/replay_dlq.py list | inspect | replay` |
| Alert | Any DLQ depth > 0 |

Base 4 rather than 2 because the failures worth waiting for — a database
failover, a broker restart — take tens of seconds. Doubling would spend
all five attempts inside the first thirty seconds.

## 7. Data register

100 tables. **Backup coverage is 100%**: `pg_dump` takes the whole
database nightly; there is no per-table opt-in that could forget one.

Retention is stated per class below. Where it says *indefinite*, that is
a decision — the record is expected to outlive the thing it describes —
not an oversight.

| Class | Example tables | Owner | Retention |
|---|---|---|---|
| Tenancy | `companies`, `users`, `agents`, `departments`, `teams` | Backend | Indefinite (soft-delete) |
| Conversations | `conversations`, `messages`, `message_attachments`, `internal_notes` | Backend | **Indefinite — see [L-4](./v1.0-known-limitations.md)** |
| Customers | `customers`, `customer_activity`, `customer_internal_ratings` | Backend | Indefinite; erasable on request |
| Routing | `queues`, `services`, `routing_rules`, `sla_policies` | Backend | Indefinite (config) |
| Knowledge | `knowledge_articles`, `faqs`, `quick_replies` | Backend | Indefinite (content) |
| Billing | `invoices`, `ledger_entries`, `usage_records`, `financial_audit_events` | Backend | **Indefinite — statutory** |
| Audit | `audit_logs` | Security | **Indefinite — deliberately exempt from all pruning** |
| Intelligence | `learning_*`, `embeddings` | Backend | Indefinite; regenerable |
| Operational | `scheduler_runs` | Platform/DevOps | **30 days** |
| Operational | `event_outbox` | Backend | **7 days, dispatched rows only** |

**Three tables grow with traffic and have no retention**: `messages`,
`audit_logs`, `usage_records`. At pilot volume this is fine and the
growth is measurable; it is recorded as
[L-4](./v1.0-known-limitations.md) with the trigger for revisiting it.

## 9. Security posture

| Control | Implementation |
|---|---|
| Authentication | JWT bearer; access + refresh; refresh tokens in Redis |
| Authorization | RBAC, permission-per-action, resolved server-side |
| Tenant isolation | Company scope on every query |
| Feature gating | 6 commercial flags at the API boundary |
| Secrets | Environment-supplied; channel/ERP credentials encrypted at rest |
| Audit | Append-only, every domain event, exempt from retention |
| Rate limiting | Per-identity, Redis-backed |
| Transport | TLS at nginx |
| Metrics exposure | `/metrics` restricted to private ranges — verified 403 from outside |
| Backups | Secrets archive AES-256 encrypted |
| CORS | Explicit origin allowlist; wildcard refuses to boot |

|---|---|---|

## 11. What is deliberately not built

Recording these prevents rediscovery and re-argument:

- **No horizontal scaling beyond nginx round-robin.** Single host.
- **No standby / replica.** Recovery is provision-and-restore.
- **No WAL archiving.** RPO is the backup interval by design, for now.
- **No automated restore.** A false-positive automated restore is worse
  than a slow manual one.
- **No v2 API.** The `api/v1` package is the only surface; `api/v2` as a
  sibling is the intended path when needed.
- **Learning Platform Phase 3 is not built.** The intelligence layer
  observes and clusters; it writes no Memory, creates no Knowledge
  suggestions, emits no candidate events. This is a deliberate gate.

## 12. How to use this baseline

**Before building anything**, check §4 Invariants. If the change
contradicts one, stop and argue it explicitly.

**When adding a service**, it needs all five: owner, health check,
metrics, logs, alert. The guard test enforces four; the alert is on you.

**When adding an event**, add it to the
[Event Catalogue](../architecture/event-catalogue.md) in the same commit.

**When adding a table**, decide its retention and put it in §7. "Keep
forever" is a valid answer that must still be written down.

**When adding configuration**, put it in `.env.example` *and* make sure
something reads it — RC1 found two variables that were advertised and
ignored.
