# Release Candidate 1 — Final Engineering Audit

**Date:** 2026-08-06
**Commit audited:** `08a9147`
**Method:** every claim below was produced by querying the running stack,
parsing the source, or reading the live database — not by reading the
documentation that describes them. Where a check found a gap, the gap is
stated rather than softened.

**Result:** 6 of 10 audit points pass outright. 4 pass with findings.
None of the findings block the release; three of them are documentation
defects that this release closes, and three are recorded as accepted
limitations with named remedies.

## 1. Migration rollbacks — PASS

87 migrations, single head (`b7e4f2a86c15`), no branches.

```
migrations with a real downgrade : 83
missing downgrade()              : 0
empty / pass / raise             : 4
```

The four empty downgrades are **data** migrations, and each one explains
in its own body why reversing it is not meaningful:

| Migration | Why it is irreversible |
|---|---|
| `3000cabd1c86` RBAC permission sync | Reconciles granted permissions additively; no "before" state is recorded, so undoing would mean guessing which rows pre-existed. |
| `6b6f167ff303` soft-delete orphaned agent users | The pre-migration state *is* the bug; restoring it would re-block the email addresses the upgrade freed. |
| `d1f7a3c85b92` catch-all routing backfill | Removing the catch-all would restore the state where a conversation can arrive with nowhere to go. |
| `f4b8c1d05e37` repair ledger enum names | Putting unreadable labels back restores a defect. |

This is the correct pattern: a schema migration must be reversible, a
data repair need not be, and the distinction should be argued in the
file rather than assumed. **No action.**

## 2. Public API documentation — PASS

Measured against the live OpenAPI schema, not the source:

```
endpoints            : 330
paths                : 256
tags                 : 41
without summary/desc : 0
schemas              : 448
```

Every operation carries a summary or description. The schema is
generated, so it cannot drift from the implementation — which is why
[`docs/api/README.md`](../api/README.md) deliberately documents
*conventions* rather than duplicating endpoint signatures.

**No action.** See also the new
[Mobile Integration Guide](../api/mobile-integration-guide.md), which
audits the same surface from a mobile client's point of view.

## 3. Event documentation — WAS FAILING, now closed

The platform emits **99 distinct event types**. Before this release,
`event-bus.md` named **7** of them. The other 92 were undocumented: no
list of what exists, no payload description, no statement of which
consumer reacts to which.

That matters more than a missing reference page. The event bus is how
every asynchronous behaviour in the platform is triggered, and an
undocumented event is one nobody can reason about when deciding whether
a new consumer would double-handle it.

**Closed by [`docs/architecture/event-catalogue.md`](../architecture/event-catalogue.md)**,
which lists all 99 with their producers and consumers, generated against
the source and the live broker bindings.

## 4. Background workers — PASS

**19 scheduled tasks** on Celery beat and **12 event consumers**, each a
separate process with its own queue.

Every beat entry is named, its interval is explicit, and the intervals
are now *exported as metrics* so staleness can be judged per task rather
than against a single global threshold. Full listing in the
[V1.0 Baseline](./v1.0-baseline.md#background-workers).

**No action.**

## 5. Environment variables — FINDINGS

`Settings` declares **116 fields**; `.env.example` declares **78 entries**.
The difference is mostly benign — a setting with a sensible default does
not need to appear in the template. Two real problems:

### 5a. Five variables are missing from `.env.example` 🔴

```
ALERT_CRITICAL_WEBHOOK_URL     missing
ALERT_WARNING_WEBHOOK_URL      missing
BACKUP_REMOTE                  missing
BACKUP_PASSPHRASE              missing
BACKUP_RETENTION_DAYS          missing
```

These were introduced by the operational hardening release and never
added to the template. Two of them (`ALERT_CRITICAL_WEBHOOK_URL`,
`BACKUP_PASSPHRASE`) are named as **go-live conditions** in the readiness
review — so an operator working from `.env.example` would not find the
variables the checklist tells them to set.

**Closed by this release** — see
[Production Deployment Guide](../deployment/production-deployment-guide.md).

### 5b. Two advertised variables do nothing 🔴

```
PAYPAL_ENVIRONMENT                        consumed nowhere
BILLING_FAILED_PAYMENTS_BEFORE_SUSPEND    consumed nowhere
```

`PAYPAL_ENVIRONMENT` is the dangerous one. The real setting is
`PAYPAL_SANDBOX` (a boolean). An operator who sets
`PAYPAL_ENVIRONMENT=live` and restarts would reasonably believe they had
switched to live payments — and would still be in sandbox, taking no real
money, with nothing reporting an error.

Configuration that is advertised and ignored is worse than configuration
that is absent: the absent one prompts a question, the ignored one
produces false confidence.

**Recorded in the [Technical Debt Register](./v1.0-technical-debt.md#td-1).**
The fix is to delete both lines from `.env.example`; it is a one-line
change deliberately not made in a documentation-only release.

## 6. Feature flags — PASS

Six flags, all defined in `domain/features.py` — one place, with a key,
a human name, and a default:

| Key | Name | Default |
|---|---|---|
| `ai` | AI Engine | enabled |
| `erp` | ERP Integration | enabled |
| `workflows` | Workflow Engine | enabled |
| `knowledge_base` | Knowledge Base | enabled |
| `sla` | SLA Management | enabled |
| `reports_export` | Report Export | enabled |

These are **commercial** flags — "did this company buy it" — enforced at
the API boundary by `require_feature(...)` and used by the sidebar to
hide what a tenant does not have. They are distinct from RBAC, which asks
whether the *user* may act. Documented in the
[Administrator Guide](../guides/administrator-guide.md#feature-flags).

**No action.**

| **Owner** | ❌ **none existed** | No `CODEOWNERS`, no register. Closed by the [V1.0 Baseline](./v1.0-baseline.md#service-register). |
| **Alert** | ⚠️ **20/32** | See below. |

### 7a. Twelve services have no alert 🟠

Alerted: backend, postgres, redis, rabbitmq, celery-worker, celery-beat,
minio, node-exporter, and all 12 consumers (collectively, via the
per-queue consumer-count alert).

**Not alerted:**

```
nginx            frontend         grafana        prometheus
loki             promtail         alert-sink     greenmail
minio-init       postgres-exporter  redis-exporter  celery-exporter
```

Two groups matter:

- **nginx is the edge.** If it stops, nothing is served — and nothing
  fires, because Prometheus scrapes the backend directly and would still
  see it healthy. The outage would be invisible to the monitoring stack
  and visible only to customers.
- **The monitoring stack does not monitor itself.** Exactly one rule uses
  `up{job=...}`, and it watches MinIO. If Prometheus, Grafana, Loki or
  Promtail stops, every dashboard goes quiet and every alert stops firing
  — which looks identical to a healthy platform. This is the same class
  of silent failure the last release was built to eliminate, one layer up.

**Recorded as [TD-2](./v1.0-technical-debt.md#td-2).** The remedy is
small — a generic `up{job=~".+"} == 0` rule plus a blackbox probe through
nginx — but it is implementation, and this release is documentation only.

## 8. Queue coverage — PASS

All 12 consumer queues, verified against the live broker rather than the
source:

```
24 retry/DLQ queues declared  (12 × .retry + 12 × .dlq)
```

| Property | Implementation |
|---|---|
| Retry policy | 5 attempts, exponential backoff 1s → 4s → 16s → 64s → 256s, capped at 300s |
| DLQ | `<queue>.dlq`, durable, with failure reason, traceback and correlation id in headers |
| Replay | `scripts/replay_dlq.py` — `list`, `inspect` (non-destructive), `replay` (fresh retry budget) |
| Alert | Fires on any DLQ depth above zero |
| Guard | A test fails the build if a consumer is added without registering it in the replay tool |

Drilled end to end against the live broker: a deliberately failing
handler retried at 1s and 4s, then quarantined on the third attempt with
its correlation id intact.

**No action.** Procedure in the
[Operator Runbook](../deployment/runbooks.md#drain-a-dead-letter-queue).

## 9. Table coverage — FINDINGS

**100 tables**, 212 MB total.

| Property | Coverage |
|---|---|
| Backup | ✅ **100/100** — `pg_dump` takes the whole database; there is no per-table opt-in to forget. |
| Retention | ⚠️ **2/100 explicit** — `scheduler_runs` (30 d) and `event_outbox` (7 d, dispatched only). |
| **Owner** | ❌ **none existed** — closed by the [V1.0 Baseline](./v1.0-baseline.md#data-register). |

"2 of 100" reads worse than it is. Most tables hold business records that
are *supposed* to be kept — deleting a customer's conversation history on
a timer would be a defect, not hygiene. The real finding is that this was
never **stated**: 98 tables had an implicit keep-forever policy that
nobody had written down, so nobody could tell a deliberate decision from
an oversight. The [Data Register](./v1.0-baseline.md#data-register) now
states it per table.

Three tables carry genuine unbounded-growth risk and are called out in
[Known Limitations](./v1.0-known-limitations.md): `messages`,
`audit_logs`, `usage_records`.

### 9a. 156 MB of index on an empty table 🔴

The single largest object in the database:

```
embeddings          0 live rows, 0 dead rows        164 MB total
  heap                                                0 bytes
  ix_embeddings_vector_hnsw                          156 MB   (80 scans)
  other indexes                                     ~5 MB
```

**77% of the database is one HNSW index on a table with no rows in it.**

The Operational Readiness Review attributed this to table bloat and
recommended `VACUUM FULL` or `pg_repack`. That was imprecise, and the
imprecision matters: the heap is empty and already vacuumed. pgvector's
HNSW index does not shrink when rows are deleted — the graph structure
persists and is only reclaimed by a rebuild.

The targeted remedy is therefore:

```sql
REINDEX INDEX CONCURRENTLY ix_embeddings_vector_hnsw;
```

`VACUUM FULL` would also work, but takes an ACCESS EXCLUSIVE lock on a
table that does not need rewriting.

This matters right now because **the host disk is 93% full**. Reclaiming
156 MB is the cheapest available remedy. Recorded as
[TD-3](./v1.0-technical-debt.md#td-3) and in
[Known Limitations](./v1.0-known-limitations.md).

## Verdict

The platform is **fit to tag as v1.0**. Nothing found here is
architectural, and nothing found here is a surprise the system hides from
its operators — which was the property the previous release existed to
establish.

Three items must be dealt with before the first paying tenant, none of
them engineering: set and exercise the off-host backup destination, point
critical alerts at something that wakes a person, and get the disk below
80% (starting with the 156 MB index above).
