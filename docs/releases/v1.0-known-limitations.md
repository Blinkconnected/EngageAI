# Known Limitations — v1.0

What this release does **not** do, and what it does with caveats worth
knowing before a customer discovers them.

A limitation here is a **decision**: something considered, judged
acceptable for this release, with a stated trigger for revisiting.
Anything that is simply wrong belongs in the
[Technical Debt Register](./v1.0-technical-debt.md) instead.

Nothing on this page is hidden from operators at runtime. Where a
limitation can bite, something alerts.

---

## Blocking for go-live

### L-3 · The off-host backup leg has never actually run 🔴

`scripts/backup_all.sh` rsyncs each backup set to `BACKUP_REMOTE`, and
that code path is written, reviewed and typed — but `BACKUP_REMOTE` is
unset on the current host, so **it has never executed against a real
destination**. Every backup taken so far exists only on the machine it
protects.

A backup on the same disk as the database covers exactly one failure mode
(somebody dropped a table) and none of the ones that destroy a platform.

**Before the first tenant:**

```bash
sudoedit /etc/blinkengage/backup.env       # set BACKUP_REMOTE, BACKUP_PASSPHRASE
sudo systemctl start blinkengage-backup.service
ssh backup@host ls /srv/blinkengage/       # confirm the set arrived
```

**Also store `BACKUP_PASSPHRASE` off this host.** It decrypts the `.env`
inside every backup set. Lost with the host, every backed-up credential
is unrecoverable — the backups would restore a platform that cannot
start.

## Accepted for this release

### L-1 · RPO is 24 hours

Backups run nightly at 02:30 UTC. In a total-loss scenario, **up to a
day of conversations, messages and attachments is gone.**

This is a deliberate trade. Closing it means WAL archiving or streaming
replication — a change to how the database is deployed, not a script.

**Revisit when:** the platform carries revenue-critical volume, or a
customer contract specifies a tighter RPO. Either makes continuous
archiving the correct next investment.

### L-2 · Single host, no standby

There is no warm replica. Recovery from host loss means provisioning a
new machine and restoring — which is the bulk of the realistic 30–60
minute RTO, far more than the 4.8 s the restore itself takes.

**Revisit when:** an availability commitment is made to a customer, or
the platform outgrows one machine for capacity reasons. Note these are
different triggers with different answers: availability wants a standby,
capacity wants horizontal scaling.

### L-4 · Three tables grow without retention

`messages`, `audit_logs` and `usage_records` grow with traffic and have
no pruning policy.

For two of them that is correct and should not change: an audit trail is
meant to outlive the records it describes, and `usage_records` underpins
invoices that must remain reproducible. `messages` is the open question —
it is conversation content, and whether a three-year-old WhatsApp thread
should still be stored is a customer and jurisdiction question, not an
engineering one.

**Current growth is measurable and small**: 218 messages, 1,566 audit
rows, 239 usage records at baseline. Disk is monitored and alerts.

**Revisit when:** the disk alert fires for a reason other than
[TD-3](./v1.0-technical-debt.md#td-3), or a customer asks for a data
retention commitment.

### L-5 · Restore is a manual procedure

Recovery is a person reading
[disaster-recovery.md](../deployment/disaster-recovery.md) and running
the steps. Deliberate at this maturity: an automated restore that fires
on a false positive is a worse failure than a slow deliberate one.

**Revisit when:** RPO work happens. Automating restore before that would
automate recovery to a 24-hour-old state, which is not obviously an
improvement.

### L-6 · The measured RTO does not describe an outage

The rehearsal measured **4.8 s** to restore all four asset classes. That
number is true and narrow: it is the restore phase only, on a 1.5 MB dump
and 4.3 MB of objects, on a host that was already running.

It excludes detection, the decision to fail over, provisioning a
replacement, fetching backups from off-host, container start-up,
migrations and DNS cutover. **Plan for 30–60 minutes.**

Restore time scales roughly linearly with data. At 10 GB of attachments
expect tens of minutes, dominated by transfer rather than by restore.
**Re-run `scripts/dr_rehearsal.sh` after significant growth** — it is the
only thing that keeps the published number honest.

### L-7 · The intelligence layer is read-only by design

The Learning Platform observes conversations, clusters them, and detects
trends and anomalies. It **does not** write Memory facts, create Knowledge
suggestions, trigger human review, call the reasoning engine, or emit
candidate events.

This is a gate, not an omission. Phase 3 opens it, and its entry criteria
are unmet: fewer than 1,000 production observations and fewer than 50
stable clusters exist today.

**Revisit when:** the pilot produces the observation volume the
[shadow validation](../architecture/learning-platform-shadow-validation.md)
requires.

### L-8 · No mobile application

The platform is a responsive web application. There is no native client.

The API is closer to supporting one than the absence of an app suggests.
Device registration (`/api/v1/notifications/devices`), FCM push delivery,
JWT refresh, and an agent WebSocket (`/api/v1/ws/agent`) all exist and
work today.

The real gaps are narrower: **FCM only** — there is no APNs sender, so
iOS push requires routing through Firebase; **no delta-sync endpoint**,
so a client returning from offline must re-page rather than ask "what
changed since"; and **the WebSocket contract is absent from OpenAPI**,
because FastAPI does not document WebSocket routes — a mobile developer
reading the schema would not know real-time exists.

Full audit in the
[Mobile Integration Guide](../api/mobile-integration-guide.md).

### L-9 · Documentation and interface are English-first

The product interface supports English and Arabic including RTL. Product
documentation is English only.

### L-10 · One deployment topology

Docker Compose on a single Ubuntu host is the only topology that has been
built, tested and rehearsed. Kubernetes manifests, multi-region, and
managed-database variants do not exist.

**Revisit when:** a customer's procurement requires a specific topology.
Building one speculatively would mean maintaining a deployment nobody
runs.

## Not limitations

Recorded because they are regularly mistaken for gaps:

- **Only 2 of 100 tables have retention.** The other 98 hold records that
  are supposed to be kept. See the
  [Data Register](./v1.0-baseline.md#data-register).
- **Most events have no bespoke consumer.** Every event is audited and
  available as a workflow trigger; that is often all it needs. See the
  [Event Catalogue](../architecture/event-catalogue.md).
- **`/docs` and `/redoc` are disabled in production.** An unauthenticated
  API map is reconnaissance. Use a staging deployment.
- **Four migrations have empty downgrades.** They are data repairs, and
  each says why reversing is not meaningful.
