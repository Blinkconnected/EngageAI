## What this release is

The first release of Blink Engage intended to be run in production for
real customers.

The platform has been functionally complete for some time. What makes
this the production release is not new capability — it is that the
platform can now be **operated**: failures are visible, data is
recoverable, and no single bad message or unbounded container takes it
down.

## The platform in one paragraph

An enterprise omnichannel customer engagement platform. Customers reach a
company through WhatsApp, Facebook Messenger, Instagram, Telegram, email,
SMS or web chat. Those messages become conversations, routed to queues,
assigned to agents, measured against SLA targets, and optionally answered
by AI. One deployment serves many companies, isolated at the row level.

## Highlights

### Omnichannel conversations

Seven channel types plus a plugin architecture. A customer reaching you
on two channels is one customer record. Replies go back the way the
customer came in.

### Routing that cannot drop anything

Every new workspace is created with a queue, a service, and a catch-all
routing rule at the lowest possible priority. A conversation cannot
arrive with nowhere to go, on day one, before anything is configured.
Rules an administrator writes later outrank the catch-all automatically.

### AI that knows when to stop

Reply suggestions, summarisation, translation, sentiment, auto-tagging,
grammar and tone, next best action, and knowledge search. Autopilot can
answer unattended when confidence clears a configured threshold.

It hands off rather than guessing when unsure, and stops automatically
when a conversation is in SLA trouble. OpenAI, Claude or Ollama —
Ollama runs locally, for customers who cannot send conversation content
to a third party.

### SLA with four clocks

First response, next response, resolution, idle — each pausing outside
business hours.

### Intelligence, read-only

The platform clusters resolved conversations and reports patterns, trends
and anomalies. In this release it observes and writes nothing back. That
is a deliberate gate, not an omission.

### Enterprise controls

RBAC per action, tenant isolation enforced on every query, credentials
encrypted at rest, an append-only audit trail covering all 99 event
types, rate limiting, and a metrics endpoint reachable only from the
monitoring network.

## Operational capability

This is what changed most recently, and it is why the release exists.

| Capability | State |
|---|---|
| **Alerting** | 12 rules, severity-routed. Verified by firing a real alert through the real notification policy and confirming arrival. |
| **Dead-letter queues** | All 12 consumer queues: 5 attempts, exponential backoff, quarantine with traceback, replay tooling. Drilled against the live broker. |
| **Backups** | Nightly: database, object storage, configuration, and an encrypted `.env`. Checksummed, retained, off-host capable. |
| **Disaster recovery** | Rehearsed and timed. All four asset classes restored and verified, including serving objects from a restored MinIO. |
| **Correlation IDs** | Threaded from HTTP request through outbox, queue, consumer and Celery task. |
| **Retention** | Operational tables pruned daily. Undispatched events never deleted, at any age. |
| **Resource bounds** | Every production service has a memory limit, restart policy, health check and log rotation — enforced by a build-failing test. |

### What the hardening found

Worth stating, because it is the argument for why this release matters:

- **All twelve alert rules were incapable of evaluating.** They
  referenced their datasource by name where an internal identifier was
  required. Every rule was provisioned, visible, and silently returned
  "data source not found" on every evaluation. The platform did not have
  alerting pointed somewhere useless — it had no working alerting.
- **The log dashboards were pointed at a datasource that did not exist**,
  for the same reason.
- **Three of the new alerts had no data to read.** No host metrics
  collector, object storage unscraped, and per-queue depth unavailable on
  the endpoint being scraped — so the dead-letter alert matched nothing
  and reported "no data" forever.
- **On its first working day the fixed alerting found a real problem:**
  the host disk is 93% full.

## Before you deploy

Three items, none of them engineering. All three are in the
[Deployment Guide](../deployment/production-deployment-guide.md).

1. **Set and exercise the off-host backup destination.** The rsync path
   is written but has never run against a real destination. Until it has,
   backups do not survive host loss.
   Store `BACKUP_PASSPHRASE` somewhere other than the platform host.
2. **Point critical alerts at something that wakes a person.** They
   currently land in an on-host sink nobody watches at 03:00.
3. **Get the disk below 80%.** It is at 93%. Start with
   [TD-3](./v1.0-technical-debt.md#td-3) — a 156 MB index on an empty
   table, reclaimable with one `REINDEX`.

## Known limitations

Summarised; full detail in [Known Limitations](./v1.0-known-limitations.md).

- **RPO is 24 hours** — nightly backups.
- **Single host, no standby** — recovery means provisioning a new machine.
- **No mobile app** — the API is close, with three named gaps.
- **Intelligence is read-only** — Phase 3 is gated.
- **Restore is manual** — deliberately.
- **One deployment topology** — Docker Compose on Ubuntu.
