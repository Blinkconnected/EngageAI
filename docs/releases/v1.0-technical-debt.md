# Technical Debt Register — v1.0

Things that are **wrong**, as opposed to things that are bounded. A
bounded trade-off with a stated trigger belongs in
[Known Limitations](./v1.0-known-limitations.md); this page is for
defects, misleading configuration, and coverage that looks like coverage
and is not.

Each entry states what is wrong, what it costs, what the fix is, and how
much work the fix actually is. Estimates are deliberately included: debt
without a cost estimate never gets prioritised, and most of these are
smaller than they look.

**Ordering is by severity, not by discovery.**

---

## TD-1 · Two environment variables are advertised and dead 🔴

**Severity:** High — silently wrong behaviour in payments
**Effort:** 5 minutes
**Found by:** RC1 audit, point 5

`.env.example` declares two variables that **nothing reads**:

```
PAYPAL_ENVIRONMENT
BILLING_FAILED_PAYMENTS_BEFORE_SUSPEND
```

The first is the dangerous one. The setting that actually controls PayPal
mode is `PAYPAL_SANDBOX`, a boolean. An operator who reads
`.env.example`, sets `PAYPAL_ENVIRONMENT=live`, restarts, and watches the
service come up healthy would have every reason to believe they had
switched to live payments.

They would still be in sandbox. Taking no real money. With nothing
reporting an error.

Configuration that is advertised and ignored is worse than configuration
that is absent: the absent one prompts a question, the ignored one
produces confident silence.

**Fix:** delete both lines from `.env.example`. If a
`PAYPAL_ENVIRONMENT`-style string setting is genuinely wanted, add it to
`Settings` and derive `paypal_sandbox` from it — but the boolean already
works, so deleting is the smaller correct change.

**Guard worth adding:** a test asserting every non-infrastructure key in
`.env.example` maps to a `Settings` field. That is the mechanism that
stops the third one appearing.

## TD-3 · 156 MB HNSW index on an empty table, on a 93%-full disk 🔴

**Severity:** High — the host is close to full
**Effort:** one `REINDEX`, minutes
**Found by:** RC1 audit, point 9

```
embeddings          0 live rows, 0 dead rows       164 MB total
  heap                                               0 bytes
  ix_embeddings_vector_hnsw                        156 MB   (80 scans)
```

**77% of the 212 MB database is one index on a table with nothing in it.**

The Operational Readiness Review recorded this as table bloat and
recommended `VACUUM FULL` or `pg_repack`. That diagnosis was imprecise
and the imprecision matters: the heap is empty and already autovacuumed.
pgvector's HNSW index does not shrink when rows are deleted — the
proximity graph persists and is reclaimed only by a rebuild.

**Fix:**

```sql
REINDEX INDEX CONCURRENTLY ix_embeddings_vector_hnsw;
```

`VACUUM FULL` would also reclaim it but takes an ACCESS EXCLUSIVE lock to
rewrite a table that has no rows to rewrite.

**This is urgent for a reason unrelated to the database.** The host disk
is at 93% (2.6 GB free) and the disk alert is firing. Reclaiming 156 MB
is the cheapest single remedy available.

**The deeper question:** why does `embeddings` have zero rows? Either the
knowledge base is genuinely empty on this host, or something deleted the
embeddings and the reindex sweep has not repopulated them. Worth
answering before assuming the index is simply stale.

## TD-2 · nginx and the monitoring stack are not alerted on 🟠

**Severity:** Medium — silent failure of the thing that reports failure
**Effort:** ~1 hour
**Found by:** RC1 audit, point 7

Twelve of 32 services have no alert. Two groups matter.

**nginx is the edge.** If it stops, nothing is served. Nothing fires:
Prometheus scrapes the backend directly and continues to see it healthy,
so the 5xx and latency rules stay quiet. A total outage would be visible
to customers and invisible to the monitoring stack.

**The monitoring stack does not monitor itself.** Exactly one alert rule
uses `up{job=...}`, and it watches MinIO. If Prometheus, Grafana, Loki or
Promtail stops:

- dashboards go blank,
- alerts stop firing entirely,
- and the result is indistinguishable from a healthy, quiet platform.

This is precisely the silent-failure class the previous release was built
to eliminate, one layer up. The alerting now works; nothing checks that
it still works tomorrow.

**Fix — two rules and a probe:**

1. A generic scrape-target alert:
   ```
   up{job=~".+"} == 0     for: 5m     severity: critical
   ```
   This covers every current and future scrape target at once, which is
   better than one rule per service.
2. A blackbox probe **through nginx** to a real route, so the edge is
   proven end to end rather than by container liveness.
3. Add `blackbox-exporter` to the monitoring tier (it is the standard
   component for 2; writing a bespoke prober would be worse).

**The uncomfortable part:** an alert about Prometheus being down cannot
be evaluated by Prometheus. Full coverage needs an external dead-man's
switch — a heartbeat pushed to a third-party service that alerts on
*absence*. Worth doing before a real on-call rotation exists; recorded
here so the limitation of the two rules above is not mistaken for
completeness.

## TD-4 · Two tests fail at HEAD, unrelated to any release 🟠

**Severity:** Medium — a red build teaches people to ignore red builds
**Effort:** unknown; owned by the in-flight work that caused it
**Found by:** RC1 verification

```
FAILED tests/unit/test_routing_decisions.py::test_every_reason_code_has_a_decision_and_a_sentence
FAILED tests/unit/test_version_consistency.py::test_changelog_pyproject_and_package_json_versions_match
```

Both fail at `HEAD` independently of the operational-hardening release —
verified by running them in a clean worktree at `HEAD` with no changes
applied. They belong to concurrent in-flight work.

**Why it is on this register anyway:** the project rule is "never
continue with broken tests", and RC1 shipped with two failing. The
justification is that they are somebody else's uncommitted-work
casualties, not regressions — but a persistently red suite is how a team
learns to stop reading test output, and that habit costs far more than
these two tests.

**Fix:** whoever owns the routing-decision and version-consistency
changes should land or revert them. RC1 should not be tagged while the
suite is red.

## TD-5 · The frontend left navigation is a flat list of 17 items 🟠

**Severity:** Medium — usability, and it slows onboarding
**Effort:** ~half a day
**Found by:** user report during RC1

`navConfig.ts` renders seventeen top-level entries with no grouping:

```
Dashboard  Inbox  Customers  Agents  Departments  Channels  Status
Services  Queues  Roles  SLA  Intelligence  Reports  Billing  ERPNext
Settings
```

They are not the same kind of thing. Inbox and Customers are daily work.
Agents, Departments and Roles are organisation setup done once. Services,
Queues and SLA are routing configuration. Reports, Intelligence and
Billing are analysis. Presenting them as one flat list makes a new
administrator scan sixteen items to find the one they need, and gives no
hint about which ones must be configured before the platform will route
anything.

`Services` and `Queues` even share an icon, which is a fair signal that
they belong together.

**Fix:** a proposed information architecture with rationale is in
[navigation-information-architecture.md](../architecture/navigation-information-architecture.md).
It is a `navConfig.ts` restructure plus a collapsible group component —
no routing or permission changes.

## TD-6 · `scheduler_runs` is 22 MB of telemetry on a full disk 🟡

**Severity:** Low — bounded, remedy already deployed
**Effort:** none; wait one sweep
**Found by:** RC1 audit, point 9

47,282 rows, 22 MB — the second-largest object in the database, holding
records *about* the platform running rather than records the platform is
for.

Retention (30 days) shipped in the previous release and runs daily, but
the sweep has not yet pruned to steady state.

**Action:** none, beyond confirming the row count falls after
`prune-operational-tables` next runs. If it does not, the retention task
is not working and this becomes a real defect.

```bash
docker compose exec -T postgres psql -U blinkengage -d blinkengage \
  -c "SELECT count(*), min(started_at) FROM scheduler_runs;"
```

## TD-7 · Consumer health checks prove existence, not consumption 🟡

**Severity:** Low — a second signal already covers it
**Effort:** ~2 hours
**Found by:** carried forward from operational hardening

The consumer health check greps `/proc` for the consumer module. It
proves the process exists. It does not prove the process is still
consuming — a consumer wedged on a permanently-blocked `await` would pass
its health check indefinitely.

**Mitigated, not fixed:** the per-queue consumer-count alert is the
authoritative signal, and RabbitMQ removes a consumer registration when
the connection dies. A wedged process that keeps its AMQP connection open
would still evade both.

**Fix:** have each consumer touch a heartbeat file after every processed
message and have the health check assert freshness. Small, and it turns a
liveness check into a real one.

## TD-8 · No CODEOWNERS file 🟡

**Severity:** Low
**Effort:** 15 minutes
**Found by:** RC1 audit, point 7

Ownership is now stated in the
[V1.0 Baseline](./v1.0-baseline.md#service-register), which is a document
nobody is forced to read. `.github/CODEOWNERS` puts the same information
where it is enforced — on the pull request.

**Fix:** add `.github/CODEOWNERS` mapping the baseline's ownership onto
paths, once the roles map to real GitHub teams.
